# PatchBound: Executive Verdict

**Audit date:** 2026-11-01  
**Recommendation:** **G — ABANDON PatchBound as a standalone product in its current form.**  
**Scope:** Repository and local behavior audit. The implementation was not modified. The six files in this audit directory are the only intended deliverables from this audit.

## Assessment

PatchBound targets a real engineering problem: an automatically generated change can satisfy one reported failure while breaking other behavior, and users need evidence before accepting it. The repository does not show that PatchBound has solved that problem reliably enough to justify another six months of product engineering.

The product promises a deterministic trust boundary around AI-generated code repair. The implemented path does not provide that boundary. Test commands run as ordinary local subprocesses; the verifier ignores the command exit code; a user-supplied reproduction command can be promoted to “V3 / CI clean”; and the approval node labels a hash generated by the program as human approval. These are not peripheral defects. They invalidate the product’s principal reason to exist.

The practical core is much smaller: a Python CLI that runs one supplied test command in a disposable Git clone, locates candidate code with simple heuristics, applies an anchored edit, and emits a patch/report. The strongest demonstrated repair is a synthetic arithmetic example. The benchmark includes direct-patch fixtures and does not establish general repair quality. No user research, usage, retention, willingness-to-switch, or real-repository success evidence is present in the repository.

This is not a recommendation to abandon the underlying problem. It is a recommendation to stop investing in this product shape until a specific user group demonstrates that a narrow, safe workflow is valuable. If there is an adopter willing to validate that workflow, preserve the patch artifact, policy checks, and correctly recorded test evidence as prototype material. Do not continue the current broad agent, ledger, Synapse, and GitHub automation roadmap.

## Product viability

| Question | Finding |
|---|---|
| Is the problem real? | Yes. Generated changes can regress unrelated tests, and running repository code has security implications. |
| Is the pain strong enough for a new standalone product? | **Unknown.** The repository contains no customer evidence. |
| Is the current product useful today? | **Narrowly and with caveats.** It can help exercise a small tests-first repair flow; its verification and trust labels are not dependable. |
| Is there meaningful differentiation? | **Not demonstrated.** Existing coding assistants already cover issue-to-change and test workflows. PatchBound’s claimed differentiation is stronger assurance, but current implementation does not support the claim. |
| Is six months of continued engineering justified? | **No, based on available evidence.** First validate a narrow workflow with users; the current technical guarantees require substantial correction before any trust-sensitive use. |

## Technical quality

The repository is readable enough to inspect, has a basic CI definition, and has deterministic patch/policy primitives worth retaining as code. Static checks pass locally. That does not compensate for a verifier whose result can be false, a “sandbox” that is not an OS security boundary, default auto-approval, machine-specific tests, and documentation that repeatedly marks unverified or incomplete capabilities as verified.

Local verification on 2026-11-01:

- `ruff check .`: passed.
- `mypy patchbound tests`: passed for 96 source files.
- Full pytest run with the project virtualenv on `PATH`: **79 passed, 1 failed** in 73.97 seconds. The failure is `tests/unit/test_synapse_context.py::test_synapse_provider_attaches_to_synapse_project`; it hard-codes a sibling checkout and calls its status CLI, which fails when that checkout tries to write a log outside the workspace.
- An earlier run without the virtualenv on `PATH` also failed the nested benchmark invocation. Putting `.venv/bin` on `PATH` resolved that benchmark failure; it did not resolve the Synapse integration failure.
- A temporary two-test Git repository was used to exercise the workflow directly: only the targeted test command was configured, that test passed after the candidate patch, an unrelated test failed, and PatchBound still returned `V3_CI_CLEAN`. Running the whole suite in that workspace returned one failure and one pass.
- `/usr/bin/false` was also passed through the verification runner. The subprocess result retained exit code 1, while the parsed report said zero executed and zero failed. The reproduction classifier therefore interprets this kind of execution failure as “not reproducible.”

These are local checks, not a claim that the project’s GitHub Actions workflows or supported Python/platform matrix passed. No live provider call, live GitHub issue-to-PR operation, hostile-code exploit, or production deployment was attempted.

## Biggest problems

1. **ENG-01 — Critical:** The verifier can issue a false V3/CI-clean result; directly reproduced.
2. **ENG-02 — High:** “Sandbox” is a subprocess wrapper with no filesystem, network, CPU, or memory isolation.
3. **ENG-03 — High:** The claimed human gate defaults to automatic approval and does not collect a human approval event.
4. **ENG-04 / ENG-05 — High/Medium:** “Investigator,” “blind reviewer,” causal experiment, and claim-ledger positioning exceed what the connected implementation does.
5. **ENG-06 — High:** Current default provider model IDs point to models whose providers have retired them.
6. **ENG-07 / ENG-08 / ENG-09 — Medium:** Policy keys are silently ignored, temporary workspaces can collide and are not cleaned up in the workflow, and failures can be reported as successful process completion.
7. **DOC-01 — High:** Audit and product documentation materially overstates implementation status and verification evidence.

## Strongest components

- **Anchored patch representation and digest:** A constrained edit is easier to review than an opaque whole-file rewrite. Keep this only as a small, testable patch primitive; it does not by itself prove correctness or safety.
- **Basic local policy checks:** Diff-size, file-count, protected-path, and added-line checks are useful building blocks. The current YAML contract is broader than what the implementation enforces.
- **Disposable Git clone concept:** Working away from the user’s checkout is a sound default for change generation. The current scratch path lifecycle and execution isolation need repair.
- **Basic local quality automation:** Ruff, mypy, pytest, and packaging smoke tests give a starting point. The local suite’s hard-coded Synapse integration and environment-sensitive nested test show that the test boundary is not portable yet.

These are useful implementation fragments, not evidence that the complete product is viable.

## Weakest components

- The advertised verification level is not tied to a known complete test command or its exit status.
- The advertised sandbox is not safe for untrusted repository code.
- “Human approval” is a default boolean plus an unkeyed deterministic hash.
- Issue solving does not use the issue’s title/body to derive a repair; PR review does not review the diff or post a review.
- The evaluation harness does not establish repair performance on representative projects.
- Synapse, claim ledger, experiments, “blind reviewer,” and multi-stage orchestration add surface area without demonstrated outcome improvement.
- Documentation’s “all features verified” and “Cryptographic” labels encourage more confidence than the code warrants.

## Decision and investment gate

**Primary recommendation: G — ABANDON.** Stop treating PatchBound as a standalone high-assurance repair product. Do not spend six months adding capabilities to the present architecture. A short product-discovery effort may test whether one specific user segment wants a constrained patch proposal plus trustworthy test evidence. If no committed design partner or internal adopter can be identified, archive the product direction and retain only reusable code with clear ownership.

If a real adopter validates the problem, the work is a new, narrower product hypothesis: reliable command execution and test evidence first, safe execution boundary second, explicit review third, optional single-model patch proposal last. The target design is documented in [TARGET_ARCHITECTURE.md](TARGET_ARCHITECTURE.md), and contingent work is in [ROADMAP.md](ROADMAP.md).

## Evidence boundaries

**Verified:** repository structure and tracked source; local lint/type/test results above; targeted manual reproductions; current documented model IDs checked against provider deprecation pages linked in the engineering audit.

**Inferred:** likely difficulty earning user trust given incorrect assurance labels; likely poor willingness to switch without a workflow advantage. These are product judgments, not measured user findings.

**Unknown:** users, adoption, market size, support burden, live provider operation, live GitHub behavior, production reliability, hostile-code behavior outside static inspection, and performance on real codebases.
